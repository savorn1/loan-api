# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Loan Management System: a Spring Boot 3.5.14 / Java 21 multi-module Maven monorepo implementing ten microservices on Spring Cloud 2025.0.0 (Eureka discovery + Spring Cloud Gateway + OpenFeign), plus one shared library module (`common-storage`).

## Build & run commands

- Build everything: `./mvnw clean install`
- Build one module (with its dependencies): `./mvnw -pl loan-service -am clean install`
- Run all tests: `./mvnw test`
- Run tests for one module: `./mvnw -pl auth-service test`
- Run a single test class: `./mvnw -pl auth-service test -Dtest=AuthApplicationTests`
- Run a service locally: `./mvnw -pl <module> spring-boot:run` — start `discovery-server` first, then the others (each registers with Eureka on boot; `api-gateway` also expects `discovery-server` to be healthy)
- Full stack via Docker (dev): `docker compose up --build` — builds each module's `Dockerfile`. Containers connect to your **local** Postgres and Redis via `host.docker.internal`, not containerized DBs. `docker/init-db.sql` only creates the eight empty databases (`auth_db`, `customer_db`, `loans_db`, `payment_db`, `loan_product_db`, `accounting_db`, `notification_db`, `branch_db`); tables are created at runtime by Hibernate (`spring.jpa.hibernate.ddl-auto=update`). Note: `loans_db` (plural) is deliberate — your local Postgres already had an unrelated `loan_db` (singular) owned by a different project. Requires a `.env` (copy `.env.example`) — `JWT_SECRET` has no fallback, so compose fails fast if it's unset.
- Full stack via Docker (prod): `docker compose -f docker-compose.prod.yml up --build` — containerized Postgres/Redis, only `caddy` (reverse proxy + auto TLS) published to the host; every other service stays on the internal `loan-net` bridge network. Requires a `.env` next to that file (`POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `JWT_SECRET`, `DOMAIN`, MinIO/S3 vars — see `.env.example`).
- CI (`.github/workflows/ci.yml`) runs `./mvnw -B clean test` against ephemeral Postgres/Redis containers (not Testcontainers — plain `docker run` steps in the workflow); discovery-server/api-gateway aren't started since Eureka registration failures don't fail Spring context-load tests.

There is no lint command configured beyond the Maven build/compile step.

## Architecture

### Module layout

| Module | Port | Package | Datastore |
|---|---|---|---|
| discovery-server | 8761 | `com.example.discovery` | — (Eureka server) |
| api-gateway | 8080 | `com.example.gateway` | — (reactive/WebFlux) |
| auth-service | 8081 | `com.example.auth` | `auth_db` + Redis |
| customer-service | 8082 | `com.example.customer` | `customer_db` + Redis |
| loan-service | 8083 | `com.example.loan` | `loans_db` + Redis |
| payment-service | 8084 | `com.example.payment` | `payment_db` + Redis |
| loan-product-service | 8085 | `com.example.loanproduct` | `loan_product_db` |
| accounting-service | 8086 | `com.example.accounting` | `accounting_db` |
| notification-service | 8087 | `com.example.notification` | `notification_db` |
| branch-service | 8088 | `com.example.branch` | `branch_db` |

`common-storage` (package `com.example.storage`) is a shared library, not a running service — a Spring Boot auto-configuration starter (`AutoConfiguration.imports`) providing a `FileStorageService` bean backed by `S3FileStorageService` (AWS SDK, S3-compatible — MinIO in dev/prod). It's a `pom.xml` dependency of `auth-service`, `customer-service`, `loan-service`, and `loan-product-service` for avatar/document/identity-scan uploads.

Shared dependency versions/BOMs (jjwt 0.12.6, springdoc 2.8.6, spring-cloud-dependencies 2025.0.0, aws-sdk 2.42.34) are managed centrally in the root `pom.xml`; each module has its own `pom.xml` with a `parent` pointing at the root `loan-system` aggregator (packaging `pom`).

### Request flow & auth model

All external traffic enters through `api-gateway`, which routes by path prefix to the backend service (`/api/auth/**`, `/api/customers/**`, `/api/loans/**`, `/api/groups/**`, `/api/group-loan-applications/**`, `/api/payments/**`, `/api/loan-products/**`, `/api/interest-schemes/**`, `/api/fee-schemes/**`, `/api/term-templates/**`, `/api/rule-templates/**`, `/api/document-templates/**`, `/api/gl-accounts/**`, `/api/journal-templates/**`, `/api/accounting-schemes/**`, `/api/financial-periods/**`, `/api/journal-entries/**`, `/api/trial-balance/**`, `/api/reconciliation/**`, `/api/reports/**`, `/api/budgets/**`, `/api/notifications/**`, `/api/branches/**`) via Eureka service discovery (`lb://<service-name>`). `AuthenticationFilter` (a `GlobalFilter` in api-gateway) is the **only** place that verifies JWTs: it parses the `Authorization: Bearer` header with jjwt, rejects with 401 if missing/invalid, and on success injects `X-User-Name` / `X-User-Role` headers before forwarding downstream. `/api/auth/login`, `/api/auth/register`, and Swagger/docs paths bypass this filter. A `dev` profile (used by `docker-compose.yml`) additionally opens CORS for any `localhost`/`127.0.0.1` origin, for calling the gateway directly without the frontend's Nitro proxy.

Downstream services (customer, loan, payment, loan-product, accounting, notification, branch) also independently verify the JWT's signature and expiry — each has its own `JwtAuthenticationFilter` (parses `Authorization: Bearer` with jjwt using the shared secret, sets the `SecurityContext` from the token's claims if valid, otherwise proceeds unauthenticated) wired into `SecurityConfig`. Their `SecurityConfig` URL matcher is still `anyRequest().permitAll()` — authorization is enforced at the method level via `@PreAuthorize` on specific endpoints, not at the URL-matcher level — but a request that reaches a backend service directly (same Docker network, misconfigured port exposure), bypassing the gateway entirely, can no longer forge `X-User-Role: ADMIN` by just setting a header; it needs a validly-signed token. This is defense-in-depth on top of the gateway's own check, not a replacement for it — the gateway still rejects missing/invalid tokens before they reach any backend service at all. In `docker-compose.prod.yml` this is largely moot for the backend services since none of them publish a host port — `caddy` → `api-gateway` is the only path in from outside `loan-net`.

`auth-service` owns the shared JWT secret (`jwt.secret`) and issues/validates tokens (`JwtService`); the identical secret is duplicated in nine places: `api-gateway`, `customer-service`, `loan-service`, `payment-service`, `loan-product-service`, `accounting-service`, `notification-service`, and `branch-service`'s config, all copied from `auth-service`. There's no central secret management — if you rotate the secret, update all nine files (plus `.env`/`.env.example` and both compose files' `JWT_SECRET` wiring).

Three services (`customer-service`, `loan-service`, `payment-service`) also run a Redis-backed `@RateLimit` aspect (`RateLimitAspect`, `INCR`+`EXPIRE`, throws `TooManyRequestsException`) on their most sensitive write endpoint — customer creation, loan disbursement, payment creation respectively. `resolveClientIp()` trusts `X-Forwarded-For` only from a loopback or site-local (RFC1918) peer, since in `docker-compose.prod.yml` the only way to reach these services at all is through `api-gateway` on the internal `loan-net` bridge network — a genuine external caller's `remoteAddr` is never in that range, so they can't spoof the header to dodge their own limit. This is advisory rate limiting, not a hard security boundary.

### Service-to-service calls (Feign)

- `loan-service` → `customer-service`: `CustomerClient` (`GET /api/customers/{id}`)
- `loan-service` → `branch-service`: `BranchClient` (`GET /api/branches/{id}`) — used in `GroupServiceImpl` to resolve/validate branch ids on groups
- `loan-service` → `accounting-service`: `AccountingClient` (`POST /api/journal-entries/generate`, `POST /api/journal-entries/{id}/system-reverse`) — `LoanServiceImpl.recordTransaction` calls `generate` for every DISBURSEMENT/PRINCIPAL_PAYMENT/INTEREST_PAYMENT/PENALTY_PAYMENT/FEE_PAYMENT/WRITE_OFF it logs (ADJUSTMENT/SETTLEMENT have no accounting-service `TransactionType` equivalent and are skipped); `voidDisbursement` calls `system-reverse` on the `journalEntryId` `approveDisbursement` stored on the `LoanDisbursement` row.
- `loan-service` → `notification-service`: `NotificationClient` (via `LoanNotifier`) — loan status-change notifications
- `payment-service` → `loan-service`: `LoanClient` (`GET /api/loans/{id}`)
- `payment-service` → `notification-service`: `NotificationClient` (via `PaymentReminderNotifier`) — three schedulers (`DueSoonReminderScheduler`, configurable via `notification.reminder.due-soon-days`; `DueTodayReminderScheduler`; `OverdueScheduler`) drive payment reminders
- `customer-service` → `notification-service`: `NotificationClient` — `IdentityExpiryScheduler` for expiring ID documents
- `accounting-service` → `loan-service`: `LoanClient` (`GET /api/loans/reports/portfolio-summary`) — used only by `ReconciliationServiceImpl` to compare the GL's Loans Receivable control account against loan-service's own outstanding-balance total
- `accounting-service` → `notification-service`: `NotificationClient` — `ReconciliationScheduler` emails `reconciliation.alert-email` on a mismatch (unset by default; always logs a `WARN` regardless)
- `auth-service` → `branch-service`: `BranchClient` — validates a staff user's assigned branch id and resolves its display name

Feign clients call by Eureka service name (`@FeignClient(name = "customer-service")`), not hardcoded host:port, and each caller declares its own client interface/DTOs rather than sharing one — there's no shared Feign-client library. `branch-service` and `notification-service` have no outgoing Feign clients of their own; `loan-product-service` has none either and nothing else calls it yet.

### Per-service structure

Each business service (`auth`, `customer`, `loan`, `payment`, `loan-product`, `accounting`, `notification`, `branch`) follows the same layering: `controller` → `service` (interface) / `service.impl` (implementation) → `repository` (Spring Data JPA) → `entity`, plus `dto`, `exception` (`AppException` + `GlobalExceptionHandler`), and `config` (`SecurityConfig`, `OpenApiConfig`). `customer-service` additionally has a `LoggingAspect`. `customer-service`, `loan-service`, and `payment-service` each have their own `aop`/`annotation`/`RedisConfig` for `@RateLimit` (see above) — copy-pasted per service rather than factored into a shared library, so a change to the rate-limit strategy needs to be applied in three places.

`loan-service` owns `loans` (the entity itself carries the full PENDING → APPROVED/REJECTED → ACTIVE → CLOSED lifecycle) plus a separate pre-approval workflow: `loan_applications` (`Application` entity — named to avoid colliding with the module's own Spring Boot bootstrap class, `com.example.loan.LoanApplication`) with child tables `loan_application_documents`, `loan_application_notes` and `loan_application_approvals`. A customer submits an `Application` (SUBMITTED); once an `ApplicationApproval` row with decision `APPROVED` is recorded (`POST /api/loans/applications/{id}/approvals`), `ApplicationServiceImpl` creates the actual `Loan` directly in `APPROVED` status — using the approver's `approvedAmount`/`approvedInterestRate`/`approvedTermMonths`, which may differ from what was originally requested — and links it back via `Application.loanId`, skipping `Loan`'s own redundant `PENDING`/`approve()` step. A `REJECTED` decision just marks the application `REJECTED`; no loan is created.

`loan-service` also owns a parallel **group lending** workflow, independent of `Application`/individual loans: `Group` (`loan_groups`, joint-liability group with a `leaderCustomerId`, `branchId`, ACTIVE/INACTIVE/CLOSED status) has many `GroupMember`s (LEADER/MEMBER, ACTIVE/LEFT); a `GroupLoanApplication` (`group_loan_applications`, its own SUBMITTED → UNDER_REVIEW → APPROVED/REJECTED/WITHDRAWN lifecycle, unrelated to `Application`) has many `GroupLoanMember` rows (per-member requested vs. approved amount/rate/term). Approving a `GroupLoanApplication` requires a decision for every member and creates **one `Loan` per accepted member** (not a shared/pooled loan); rejection is all-or-nothing at the application level.

`loan-product-service` owns `loan_products` (product catalog: code, version, loanType, currency, amount/term ranges, status, effective date range — no direct FK to any scheme/template). Unlike every other entity in this monorepo, `LoanProduct.id` is a `UUID` (`GenerationType.UUID`), not a `Long` identity — an explicit schema choice for this table only. Product-specific configuration is a two-layer model: five reusable, standalone catalogs — `InterestScheme`, `FeeScheme` (each with tiered detail child tables), `TermTemplate`, `RuleTemplate` (structured eligibility conditions), `DocumentTemplate` — each with its own CRUD controller and no knowledge of any product; and five join/attachment entities (`LoanProductInterestScheme`, `LoanProductFeeScheme`, `LoanProductTerm`, `LoanProductRule`, `LoanProductDocument`) that tie a `LoanProduct` to one of those catalog rows plus product-scoped overlay attributes (`priority`, `effectiveFrom`/`effectiveTo`, `isDefault`/`isMandatory`, own `status`). Versioning a product (`LoanProductServiceImpl.newVersion`) clones these attachment rows to point at the *same* catalog entries for the new version — it doesn't clone the catalog data itself.

`accounting-service` implements the double-entry books: `gl_accounts` (chart of accounts, self-referencing `parent_id` hierarchy), `journal_templates` + `journal_template_lines` (per-`TransactionType` blueprints of symbolic debit/credit "account roles"), `accounting_schemes` (binds a template's role + currency to a real `gl_account`), `financial_periods` (OPEN/CLOSED date ranges that every posting is scoped to), and `journal_entries` + `journal_entry_lines` (the actual DRAFT → POSTED → REVERSED double-entry postings, validated balanced on both create and post). `TransactionType` (DISBURSEMENT, PRINCIPAL_PAYMENT, INTEREST_PAYMENT, etc.) is the only vocabulary this service shares with loan-service/payment-service — it has no notion of a loan product; upstream services can either call `POST /api/journal-entries` directly with fully-resolved lines and an opaque `referenceType`/`referenceId` pointing back at their own domain object, or `POST /api/journal-entries/generate` to have this service resolve `transactionType` → `JournalTemplate` → `AccountingScheme` itself and post immediately (see `JournalEntryServiceImpl.generate`; idempotent on `(transactionType, referenceType, referenceId)`). `GlAccountSeeder` and `JournalTemplateSeeder` (`@Order`ed 1 and 2) seed a default USD chart of accounts + one two-line template per generate()-able TransactionType on first boot. General ledger (`GET /api/gl-accounts/{id}/ledger`) and trial balance (`GET /api/trial-balance`) are read-only reports computed from `journal_entry_lines`, not separately stored. `GET /api/reconciliation/loans-receivable` compares GL account 1100 against loan-service's portfolio total (see Feign clients above) — a mismatch means either a bug, a missed accounting call, or a manual journal entry that bypassed loan-service; loans disbursed/paid before this integration existed will show as permanent variance unless backfilled. `BudgetLine` (`budget_lines`, one row per `(financial_period_id, gl_account_id)`, company-wide — deliberately not branch-scoped, since nothing validates raw `branchId`s against branch-service) is plain CRUD; `GET /api/reports/budget-vs-actual` compares it against `TrialBalanceService.getTrialBalance` rather than querying `journal_entry_lines` directly, keeping it consistent with the trial-balance report. `GET /api/reports/income-by-branch` and `GET /api/reports/ledger-by-branch` are the other two report endpoints (no income statement, balance sheet, or cash-flow report exists).

`branch-service` is a passive reference/lookup service: `Branch` (code, name, address, status) plus `BranchBusinessHours` (one row per branch+day-of-week, upserted via `PUT /api/branches/{id}/business-hours/{dayOfWeek}`). Writes require `hasRole('ADMIN')` (it can't check finer-grained `BRANCH_*` permissions since that RBAC data lives in auth-service's DB, not the JWT); reads are open to any authenticated user. It has no outgoing Feign clients — see above for its callers.

`notification-service` is an active fan-in sink: a single `Notification` entity (`recipientType` CUSTOMER/USER, `channel` EMAIL/SMS/PUSH/IN_APP, `recipientContact` supplied by the caller — no cross-service lookup here). `POST /api/notifications` creates the record **and attempts delivery inline** (synchronous, not queued) via `DefaultNotificationSender`: `EmailSender` (real SMTP, Mailhog in dev) for EMAIL, `SmsSender` (log-only, no real gateway) for SMS; other channels or a missing `recipientContact` just log and report success. There's no service-to-service auth on `POST /api/notifications` — any valid JWT can call it.

### Orphaned code

The `src/` directory at the repository root (outside all module directories) is pre-microservices leftover code — it predates the split into services (see git history: `first commit` → `change to microservice`). It is not listed in the root `pom.xml`'s `<modules>` and is not built. Its package is `com.example.loan` but the actual content is customer-domain code (the ancestor of `customer-service`). Safe to ignore or delete; don't confuse it with the real `loan-service` module.
